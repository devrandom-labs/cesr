# A15 integrated performance and memory baseline

Status: A15 accepted after the final release archive and full Nix gate. These are local baseline observations, with the boundaries stated below.

## Environment and measurement contract

Platform: MacBook Pro `Mac16,7`, Apple M4 Pro (10 performance + 4 efficiency cores), 24 GB RAM, macOS 26.5.2 (`25F84`), aarch64-darwin. Current commit: `de08a972b390ea640519d4dcb7343d5dc4a864b9` plus the uncommitted A01–A15 work in `docs/TODO.md`. `rustc 1.95.0 (59807616e 2026-04-14)`, LLVM 22.1.2. Cargo release profile: `opt-level = 3`, `lto = true`, `codegen-units = 1`. The command uses `--all-features` and one test thread. This is a local machine observation, not a cross-stack result.

Harness: [`a15_baseline.rs`](../../crates/keri-codec/tests/a15_baseline.rs). It is ignored by ordinary test gates and must be run explicitly in release mode. Standard cases warm up 100 full calls, then collect 101 single-call samples; the memory-hard Argon2 cases have their separately recorded 3-warmup/21-sample protocol below. It reports p10, median and p90 wall-clock nanoseconds, median byte throughput, allocation calls, requested allocation bytes, retained bytes at return and peak live bytes within the measured call. A thread-local counting `System` allocator tracks the test thread only; allocator setup, sample-vector handling and printing happen outside the measured call. `realloc` counts as one allocation request of the new size and adjusts live bytes by old/new layout size. Retained means heap allocations still live when the returned owned result is measured; it is not process RSS. Run multiple independent processes because scheduling, frequency, cache and thermal state can move the timing distribution. No magic timing threshold or security setting change is applied.

The first workload reads the pinned 1,594-byte keripy-generated icp → rot → ixn stream through public `EventMessage::parse` with explicit `MessageLimits`, binds each to `Signed`, verifies real Ed25519 signatures and SAIDs through `KeyState::incept`/`ingest`, then creates an owned `KeyStateSnapshot`. The fixture, algorithms and signed bytes are identical across samples. The snapshot is kept alive until retained bytes are recorded. This excludes persistence, network, transport scheduling and external durability; those host boundaries require separate equivalent-workload comparisons under A21–A23. `SaltyCustodian` Argon2 cost is intentionally isolated under A15.4, not mixed into the signed-fold result.

Reproduce and archive three fresh process rounds:

```sh
for sample_round in 1 2 3; do cargo test --release -p keri-codec --test a15_baseline --all-features pinned_kel_parse_bind_verify_fold_owned_snapshot -- --ignored --nocapture --test-threads=1; done > docs/audits/2026-09-30-a15-kel-release.txt 2>&1
```

The archived [raw release output](2026-09-30-a15-kel-release.txt) contains three executed passes, each with 101 samples after 100 warmups. Median latency was 154,625 / 159,458 / 155,666 ns; the corresponding p10–p90 intervals were 143,125–163,500 / 145,000–178,125 / 144,833–162,750 ns. Median throughput was 10.31 / 10.00 / 10.24 MB/s of original wire bytes. Every run reported 122 allocation calls, 13,061 requested bytes, 448 retained bytes and 5,816 peak live bytes per complete three-event fold and owned snapshot. Two initial five-warmup pilot runs differed substantially (276,333 versus 147,292 ns median); the archived 100-warmup protocol avoids using either pilot as an optimization claim.

## A15.2 first witnessed/rejected cases

The accepted case returns an owned snapshot; the rejected case returns no state. The rejection can stop before all work done by acceptance, so its lower time is a stage-cost observation, not a claim that the same cryptographic work is faster. No signature verification, SAID check or witness threshold is disabled in the accepted case.

## A15.2 signed recovery and independent scaling

The harness constructs a deterministic, genuinely Ed25519-signed four-frame recovery fixture outside the timed call: `icp → ixn1 → ixn2`, followed by a `rot` at sequence 1 that reveals the key committed by the inception and points back to that inception. The measured public path parses all four wire frames, verifies and folds the first three, obtains `SameSnVerdict::Supersedes` against the recorded interaction, replays the signed inception and recovery rotation from the host's rewind point, and retains the recovered owned snapshot. This is a validating recovery fold; the host's storage rewind, fork retention and durability are outside this benchmark. Across three processes the 1,441-byte case had median 136,833/129,125/130,750 ns, 116 allocations, 9,080 requested bytes, 272 retained bytes and 3,687 peak bytes. The [raw scaling output](2026-09-30-a15-kel-scale-release.txt) has p10/p90 and throughput.

The same archived three-process command executed all nine cases present at that point, each with 100 warmups and 101 samples:

```sh
for sample_round in 1 2 3; do cargo test --release -p keri-codec --test a15_baseline --all-features -- --ignored --nocapture --test-threads=1; done > docs/audits/2026-09-30-a15-kel-scale-release.txt 2>&1
```

The scaled inception fixture holds a real transferable commitment and threshold 1 constant. It varies current key count (1/4/8) with one real controller signature; then signature count (1/4/8) at eight keys; then witness count (4/8) with one real receipt and receipt count (1/4/8) at eight witnesses. It also repeats the exact first controller signature 8 or 64 times to measure duplicate wire work while the authentication rule counts one distinct signature. Another row distributes the same eight real signatures over 1/2/4/8 valid `-A` groups inside one V1 attachment frame. The builder, signer and public typed parser use the same cryptographic settings for every row; fixture creation is outside the timed call. All accepted rows return an owned snapshot.

The eight-signature one-group comparison uses 86 allocations and 8,848 requested bytes, versus 93 and 11,180 across eight groups, with the same 888 retained bytes. Duplicate material increases parse allocation/bytes but cryptographic verification deduplicates the identical signature. This is a measured workload observation, not a claim that arbitrary distinct invalid signatures cost the same.

To vary body bytes with a fixed two-signature, one-group-per-event fold, an interaction anchors 0/32/512/2,048 distinct digest seals after a signed inception. The [raw anchor output](2026-09-30-a15-kel-anchors-release.txt) contains three independent all-case runs of the same command, now with ten ignored cases. Allocation calls and requested/retained/peak bytes ranged from 59/4,579/272/2,079 to 4,176/1,154,746/272/511,123. The large SAD body grows transient work and memory while the owned state stays 272 bytes. The large body is legal under the explicit 8 MiB body, 8,192 field and 64 depth policy; larger hostile or rejected payloads belong to the framing/resource-limit tests and the A15.3 credential rows.

These rows complete the A15.2 evidence matrix for input bytes, attachment groups, keys, witnesses, signatures, duplicate signatures, chunks, batches, receipt accumulation, rejection and recovery. Timing remains local and noisy; the raw three-process p10/median/p90 values, not a point estimate, are the performance evidence. The later sections record A15.3–A15.5.

## A15.3 credential and TEL lifecycle matrix

The credential fixture is a legal ACDC JSON SAD generated once per case with the public `SadCodes::saidify` path for both the nested attributes block and outer credential. A deterministic Ed25519 issuer signs the exact outer bytes; each measured accepted call deserializes through public `Acdc::deserialize` under `JsonLimits(8192, 64)`, checks the credential's declared basic issuer against that verifier, verifies the genuine signature and returns an owned `Acdc<'static>`. Payload sizes are 1 KiB, 64 KiB and 512 KiB, and a separate batch holds 1/16/64 distinct 1 KiB credentials. One 64 KiB fixture has a changed payload byte without a new SAID, yielding `CodecError::Said`; another has a signature made by the wrong key, yielding `VerificationError::Signature(SignatureError::Invalid)`. These reject at different stages and retain no credential. ACDC has no TEL status fold by itself; the TEL rows below measure that lifecycle. The synthetic large fixtures exercise the supported ACDC shape but are **not** imported keripy outputs. The checked-in ACDC parity corpus remains labeled partial because its generator reproduces pinned keripy shapes without importing keripy itself.

The TEL fixture constructs a real signed issuer KEL with three accepted interaction anchors. Setup publicly parses and cryptographically folds the KEL outside the timed calls, then retains the owned issuer state and typed accepted anchors. A measured TEL call publicly parses framed V1 `-G` registry inception, issue and revoke messages, binds `SignedTel` to the exact body, checks each source coordinate and accepted KEL event seal, folds an owned `RegistryState`, issues one owned `CredentialState`, and revokes it. This backerless `NB` route correctly relies on the accepted KEL anchor; the standard does not require a redundant TEL issuer signature. Rejected calls omit the accepted issue or revoke anchor; the latter asserts the issued credential remains unchanged. A separate batch uses one management head and 1/16/64 distinct issuance TELs, each with its own validated KEL anchor, and retains every credential head. These measurements exclude KEL lookup/persistence and host credential-index storage; setup validates the KEL once and the timed route verifies the supplied accepted anchor evidence.

## A15.4 custody isolation

The custody rows use a fixed 128-bit benchmark salt, `PathConvention::Keripy`, account/rotation/key index zero (`"000"`), `Tier::Low` Argon2id13 (opslimit 2, 64 MiB) and a fixed 51-byte message. A real transferable `SaltyCustodian` with one current and one next key is incepted for setup; its signature was asserted byte-identical to an Ed25519 signature from the same salt/path/tier key pair before measuring. The rows isolate: (1) fresh `SaltyCustodian::incept`, which derives both current and next; (2) `Salt::stretch`, the one-key Argon2 operation used by that custodian; (3) `SaltyCustodian::sign`, which re-derives the current key on every call before signing; and (4) indexed Ed25519 signing with a key derived once outside measurement. The last case is a **measurement control**, not a new product key cache. The `Salt` and `KeyPair` types keep secret bytes in zeroizing storage; this work changes no secret lifetime or custody policy. A23 still owns the production custody decision.

The expensive Argon2 cases use three warmups and 21 samples per independent process, enough to report observed p10/median/p90 without spending the standard 201 calls per case on a memory-hard KDF. The signing-only control keeps the standard 100 warmups and 101 samples. The difference is printed per row in the raw output; these are deliberately separate workloads, so no subtraction of medians is presented as an isolated causal cost. For KDF/inception rows the generic `throughput_bytes_per_s` field is only the tiny salt/path input divided by time and has no useful cryptographic interpretation. Allocation counters capture the 64 MiB Argon2 work buffer, while retained bytes are measured before returned public commitments/signatures are dropped. No process RSS or secure-enclave/hardware backend is measured.

The exact command below **executed** three independent process runs of the ignored custody test; all passed. [Raw output](2026-09-30-a15-custody-release.txt) includes the p10/p90 values and allocator counts for every run.

## A15.5 final archive and verification

After the custody measurement and sampling-policy change, the final exact command `for sample_round in 1 2 3; do cargo test --release -p keri-codec --test a15_baseline --all-features -- --ignored --nocapture --test-threads=1; done > docs/audits/2026-09-30-a15-final-release.txt 2>&1` **executed** three independent full passes, each with all 15 ignored benchmark tests passing. The [final raw archive](2026-09-30-a15-final-release.txt) has 44 distinct named workload rows, each appearing three times: 132 parseable JSON results. A validation script checked each process test summary, every row's p10 ≤ median ≤ p90, and exactly three entries per named workload. Standard cases printed 100 warmups/101 samples (123 rows); the three Argon2 cases printed 3/21 (nine rows). This final archive is the baseline for future changes; earlier archives preserve the development-stage independent runs.

Focused `cargo clippy -p keri-codec --all-features --test a15_baseline -- -D warnings`, `cargo fmt --all --check` and `git diff --check` passed. The existing test-only `clippy.toml` warning about an unreachable `Matter::new_unchecked` entry did not change the protected lint policy. Direct `cargo check -p keri-codec --no-default-features --features alloc` and `cargo check -p keri-rs --no-default-features` passed as **compile-only** checks. The focused ACDC/TEL/registry integration tests above executed and passed; pinned corpus provenance remains as described in the parity ledger.

The fresh final command `nix flake check -L --option max-jobs 1 > /tmp/cesr-a15-flake.log 2>&1` exited 0 on the A15 worktree. Ten named checks rebuilt and passed: doctest, deny, no_std, WASM, format, docs, Clippy, typos, release Nextest and fuzz replay. Ten ancillary checks were reported **previously built** (YAML, TOML formatting, nixfmt, audit, function-count ratchet, deadnix, version owner, shellcheck, actionlint and KERI boundary); they were part of the successful flake evaluation but did not execute anew in this run. Nextest **executed** 2,564/2,564 tests, with 24 skipped/ignored release probes, including the 15 A15 tests explicitly executed in the final archive. Fuzz replay **executed** its available smoke targets successfully. The no_std and wasm32-unknown-unknown build matrix, including `keri-rs --example direct_mode --features wire`, **compiled only**; no WASM runtime test was claimed. The flake omitted incompatible aarch64-linux, x86_64-darwin and x86_64-linux systems on this aarch64-darwin host.

Optimization decision from this baseline: keep the existing public paths and security settings. The fixed-eight-signature group split and duplicate-signature rows identify parse allocation overhead but do not justify a production change on their own; signature count and large SAD bodies change the amount of real work, and the owned ACDC necessarily retains its payload. Custody's Low-tier 64 MiB Argon2 allocation is security policy, so no cache or weaker tier is introduced without A23's explicit secret-lifetime/trust decision. Future optimizations can compare against the final archived rows with equivalent signed bytes, accepted/rejected stage, crypto work, host durability and platform; no cross-stack speed claim is made here.
