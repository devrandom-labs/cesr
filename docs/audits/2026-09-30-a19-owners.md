# A19 invariant owners and consolidation boundary

Platform: aarch64-darwin. Source baseline: `de08a972` plus the recorded A01–A18 worktree. `docs/TODO.md` remains the acceptance queue; this inventory does not redefine it.

The [KERI draft](https://weboftrust.github.io/ietf-keri/draft-ssmith-keri.html) makes the KEL a sequence of accepted, signed events: an inception establishes authority, rotations expose prior next-key commitments and establish new authority, and each later event chains by sequence and prior digest. The issue [#149 witness contract](../superpowers/specs/2026-07-12-149-witness-semantics-design.md) specifies an ordered cut/add result and builder guard order. The approved [K6/#92 contract](../superpowers/specs/2026-07-29-k6-key-state-snapshot-design.md) requires a fallible cryptographic validating fold and a total, crypto-free fold over host-accepted events. The [P05 audit](2026-09-29-foundation.md) suggests sharing calculations only where those laws coincide.

| Law | Current owner | Boundary to preserve |
| --- | --- | --- |
| CESR qualified primitive syntax and cryptographic key encoding | `cesr`, exposed as typed `keri-events` primitives | No KEL history or host effects. |
| Event fields, static witness/backer list distinctness and nontransferable witness identity, TOAD syntax | `keri-events::member_set`, `keri-events::Toad`; `keri-codec` checked wire decoding/builders | A builder knows a caller-supplied prior witness list; a wire decoder does not authenticate a prior state. Keep existing typed builder/decoder errors. |
| Exact signed-body/event association | `keri-codec::EventMessage` on wire; `keri::Signed::from_host_asserted_parts` only for host-rehydrated or externally paired records | Never infer association from a verifying signature over unrelated bytes. |
| Controller signatures, prior-next opening, witness receipts, delegation evidence | `keri::KeyState` validating fold and the borrowed verification primitives in `authority`, `verification`, `receipt` | Validation precedes mutation; rejection leaves retained state unchanged. |
| Chain rule, cut/add membership, threshold and accepted state | `keri::KeyState` validating fold | The post-rotation witness set determines receipt authority. TEL has a parallel backer set with distinct issuer/anchor and receipt evidence. |
| Trusted replay of already accepted events | `keri::KeyStateSnapshot` | Total and crypto-free, including deterministic behavior on corrupt input; the host owns accepted-record and storage integrity. |
| Historical receipt and TEL authority | `keri::receipt`, `keri::registry`, with accepted issuer/management evidence from host | Current state cannot silently stand in for historical accepted evidence. |
| Persistence, retries, scheduling, application authorization | Host (A21–A23 integration work) | None belongs in the five pure protocol crates. |

The three materialized ordered-set calculations are `resolve_witnesses` (checked KEL), `trusted_witnesses` (trusted KEL), and `resolve_backers` (checked TEL). They all preserve surviving prior order and append new identifiers in addition order. Validation differs: KEL witnesses must be nontransferable, TEL backers follow backer list rules, and trusted replay deliberately skips bad cuts and duplicate additions rather than rejecting. Share only the ordered update algorithm through a private `keri` helper; keep each caller's validation and typed error mapping. The builder's `validate_rotation_witnesses` only needs the count after its specified guard order, so it should keep its allocation-free arithmetic instead of materializing a set.

`KeyState::apply_rotation` and `KeyStateSnapshot::rolled` also assign the same accepted fields but differ in borrowing versus ownership. A19.3 used the existing `keri-codec/tests/snapshot.rs` differential tests and added generated witnessed and delegated histories to judge whether a private common update reduces code and cognitive load without cloning borrowed values or introducing an adapter hierarchy. A no-op wrapper is not an improvement.

The assignment comparison is narrow. Both rotation paths take `sn`, current SAID, keys/threshold, next commitment, TOAD and last-establishment pointer from the accepted event, and carry prefix/config/delegator forward. The validating path stores event references in `KeyState<'e>` only **after** chain, signature, commitment, witness and delegation checks; the trusted path must own static copies and stay total on bad stored input. A common record or trait that merely re-exposes each event field would add an allocation or mapping layer without removing those distinct assignments. The ordered member update is the shared computation that can be factored without crossing that boundary. The plain-KEL property, the new 24-case witnessed cut/add property, and the new 24-case delegated-history property guard full-state equivalence on accepted histories; all executed on aarch64-linux with Rust 1.95.0. The final macOS Nix gate remains separate.

The source/API change is checkable: three materialized ordered-set loops became one `KeyState::updated_members` calculation, the trusted-only `trusted_witnesses` wrapper disappeared, and the unreachable `WitnessSetError::CutAddOverlap` variant was removed (four variants to three). The associated method is crate-private, so no new external import or public constructor was added; the public function ratchet passes. `resolve_witnesses` and `resolve_backers` remain distinct because witness eligibility, backer evidence and typed rejection ownership differ. The A15 release archive does not contain a witnessed KEL rotation or `vrt` backer rotation row, so it cannot establish a before/after runtime ratio for this change. The accepted-history properties exercise those paths for correctness, while a future performance claim would need a same-platform baseline with an identical signed rotation workload.
