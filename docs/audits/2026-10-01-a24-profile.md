# A24 protocol profile inventory and acceptance

Baseline: `de08a972` plus the A01–A20 worktree. The selected first foundation
release profile is V1 JSON/text with Selo-specific client/agent exchange.
This is an accepted profile decision and gap inventory, not an A21–A30
completion or release-readiness claim.

## Corrections to the foundation snapshot

- The foundation audit reported a GramHead code gap. The pinned CESR master
  table lists `0P`–`0S` with full sizes 32, 28, 76, and 72. The baseline
  `MatterCode` already has all four codes and matching `Sizage` entries, with
  prefix parse tests. This closes the *code-entry* observation. It does not
  demonstrate memogram application semantics or all-code coverage.
- A14 now makes the bounded V1 `MessageFramer` reject a binary cold start as
  typed `ParseError::UnsupportedColdStart`. The old audit observation about a
  binary cold start reaching the text group parser predates that fix. Direct
  `CesrGroup::parse` remains a V1 text-group API; A25 must decide a qb2 path
  or a documented conversion boundary.
- The current ACDC V1 typed model matches the imported keripy V1 `v,d,u?,i,
  ri?,s,a?/A?,e?,r?` domain. The pinned ACDC document's 2.XX `rd` and
  disclosure forms are separate profile work, not implicit V1 support.
- A literal-prefix scan over the pinned CESR V2 master table's 179 code rows
  found every named primitive/group prefix in `cesr/src/core` except the
  instantiated `-_AAACAA` genus version string, represented by the generic
  `-_AAA` counter code plus version count. This scan establishes presence of
  labels only, not correct size, qb2 representation, parsing, cryptographic
  implementation or group semantics. The specification spells the big `-S`
  source-couple row `-S#####` despite its stated eight-character layout;
  the Rust V2 table uses the normal `--S` big-code shape. Confirm this against
  keripy and executable bytes before treating it as a format divergence.
- Exact string-set comparison against pinned keripy `CounterCodex_1_0` and
  `CounterCodex_2_0` found 22/22 V1 and 59/59 V2 counter hard-code labels in
  Rust `CounterCodeV1`/`CounterCodeV2`, with no extra labels. All 22 V1 enum
  variants also occur in `cesr-stream`'s group parser source. These static
  checks do not establish payload grammar or signed-message support for each
  counter; the selected profile requires end-to-end cases for families it uses.

## V1 typed-read version boundary

`a24_profile::said_valid_unimplemented_minor_version_is_rejected_by_typed_event_read`
changes a checked inception from `KERI10` to `KERI11`, recomputes both
self-addressing digest fields, and verifies the resulting SAIDs. Before the
fix, `nix develop --command cargo test -p keri-codec --test a24_profile`
failed because typed `InceptionEvent::deserialize` accepted the 1.1 body.
The strict KEL, ACDC and EXN heads now reject syntactically valid but
unimplemented versions as typed
`VersionGrammarError::UnsupportedProtocolVersion`. A follow-up case applies
the same SAID-valid mutation to imported ACDC and IPEX EXN fixtures; both
readers reject them. `EventMessage::parse` rejects the mutated inception
through its framed public path with the same typed source. The public generic
`VersionString` and `SadCodes` remain version-neutral. The focused suite
executes 2/2 passing after the fix. The neighboring imported ACDC/IPEX,
KERI semantics, and TEL Nextest suites execute 22/22 passing; focused
all-target/all-feature Clippy exits 0. This is focused evidence, not the A24
full gate.

## Release-profile choice

The first release requires KERI/CESR 1.0 JSON, ACDC 1.0 JSON, text CESR
attachments, Ed25519/BLAKE3-256 interoperability and the required protocol
and product workflows listed in the [capability matrix](../capability-matrix.md).
This selects the already executable oracle baseline as the wire target and
keeps the first release finite. V2, native bodies, qb2/mixed message transport,
CBOR/MGPK, Ed448 verification, selective disclosure and universal
Signify/KERIA agent exchange are later-profile work. Low-level parsers may
retain their broader syntax, but typed message and verification boundaries
must report unsupported inputs deliberately. No excluded feature is called
implemented by virtue of its code-table label.

The matrix and parity ledger are reconciled against this inventory. The
selected profile's required but incomplete workflows retain their A21–A29
owners; A30 separately decides release readiness.

## Unsupported typed read boundaries

`a24_profile` now constructs a valid CESR V2 JSON version head and asserts
`MessageFramer`/`EventMessage::parse` return `ParseError::UnsupportedVersion
{ version: V2 }`; direct `KeriEvent::deserialize` returns
`VersionGrammarError::UnsupportedCesrVersion(V2)`. At every split before the
full 19-byte head, the framer waits and then rejects on completion. Before
the correction, the framed path returned a V1 grammar error.

The same suite constructs correctly sized CBOR and MessagePack V1 map heads.
The generic framer can size them, while the typed message parser reports
`UnsupportedColdStart` and direct KEL, receipt, TEL, ACDC and EXN readers
report `UnsupportedSerializationKind`. A binary cold start reports the
framer's typed unsupported-domain error and direct readers report native
`UnsupportedSerializationKind`. The write path already tests typed
unsupported-kind errors for CBOR, MGPK and native CESR. The four focused A24
tests and 349 `cesr-stream` unit tests passed.

## Algorithm inventory finding and typed exclusion

`cesr::crypto::verify` has executable verification for Ed25519,
ECDSA secp256k1 and ECDSA secp256r1 key codes. Ed448 and Ed448N key codes
are parseable. Before the A24 correction, verification returned
`VerificationError::CodeMismatch` even when the signature code was Ed448,
conflating an unavailable verifier with incompatible code material. Both
Ed448 and Ed448N exact-error regressions failed on that behavior after the
`crypto` feature was enabled (the default `cesr-rs` profile does not enable
crypto). They now return typed
`VerificationError::UnsupportedAlgorithm { verkey }`; targeted tests pass
2/2 and all-target/all-feature Clippy exits 0. Ed448 is not an advertised
verification algorithm in the working profile. If selected later, it needs
an actual verifier and independent cases.

All nine public `DigestCode` variants (BLAKE3-256/512, BLAKE2b-256/512,
BLAKE2s-256, SHA2-256/512, SHA3-256/512) have explicit digest computation
arms and per-code tests. The signed KERI/ACDC oracle profile still needs
independent vectors for each algorithm before claiming full message-level
interoperability with them.

`keri-events::MessageType` has KEL, TEL, receipt and EXN tags but no `qry`
or `rpy` value. Those exchange bodies require A26 vocabulary, codec and
acceptance rules; a transport or cache is outside the pure profile.
